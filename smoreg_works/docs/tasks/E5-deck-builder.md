# E5 — `DeckBuilder`: граф зон → секторы → шлюзы

Статус: done (2026-09-03) · Зависит от: E4 · Блокирует: E6, G7 · Оценка: 5–6 ч · Пакет: `packages/engine`

Иначе, чем в плане: секторы не делят общую рамку, а владеют ею (ребро BSP достаётся левому/верхнему
потомку), поэтому `rect` соседей не пересекаются — как требует тест — а стена между ними всё равно
толщиной 1 и шлюз остаётся ровно одним тайлом. `DeckPlan.count` необязателен, default `[4, 7]`.

Самая большая движковая задача. Ей отведён день 5 целиком; если к вечеру дня 5 property-тесты
не зелёные — см. «Откат».

## Зачем

Палуба станции — это граф зон внутри силуэта корпуса. Игрок ходит по тайлам, но структура
(что с чем соединено, через какой шлюз) должна быть настоящей и проверяемой. Существующий
пайплайн (`connectRegions`) прокладывает туннели где угодно, поэтому строитель обязан
отдать **уже связную** карту, в которой единственные проходы между зонами — шлюзы.

## Интерфейс (движок ничего не знает о содержании зон)

```ts
// sim/mapgen/deck.ts
export interface ZoneKindSpec {
  kind: string;                 // content id, e.g. "cargo"
  name: string;                 // label, e.g. "CARGO BAY"
  interior: "rooms" | "open" | "cluttered";
  weight?: number;
  /** Preferred sector size share, 1 = average. Reactor wants 1.5, a closet 0.6. */
  size?: number;
}
export interface DeckPlan {
  zones: ZoneKindSpec[];        // catalog for this depth; builder picks `count` of them
  count: [min: number, max: number];   // sectors per deck, default [4, 7]
  extraEdges?: number;          // beyond the spanning tree, default 1..2
  /** Optional: which zone kind must hold the entry / the stairs. */
  entryIn?: string; stairsIn?: string;
  /** Filled by E6. */
  vaults?: readonly Vault[]; vaultsPerZone?: number;
}
export class DeckBuilder implements MapBuilder {
  readonly name = "deck";
  constructor(planForDepth: (depth: number, rng: Rng) => DeckPlan) {}
  build(ctx: BuildContext): BuildResult   // BuildResult.zones filled, entryHint set
}
```

`MapgenOptions` получает `builder?: MapBuilder` — приоритет над `builderName` и
`builderForDepth`. `Game.enterDepth` ничего не меняет.

## Алгоритм

1. **Секторы.** BSP карты 70×34 на `count` листьев с учётом `size`; минимальный лист 12×8.
   Каждый лист — сектор; между секторами — общая стена толщиной 1 (лист включает свою
   стеновую рамку, рамки соседей совпадают).
2. **Назначение зон.** Взвешенный выбор из `plan.zones` без повторов (пока хватает), иначе с.
3. **Интерьер.** Внутри рамки:
   - `rooms` — мини-BSP на 2–5 комнат + коридоры (можно переиспользовать `RoomsBuilder` на
     под-`Grid`, если он принимает размеры; иначе простая версия здесь);
   - `open` — пол целиком, 2–6 колонн/ящиков (`Wall` 1×1 или 2×2) не у стен;
   - `cluttered` — `CavesBuilder`-подобный клеточный автомат с высокой заполненностью, затем
     `connectRegions` **внутри сектора** (написать локальную версию, ограниченную rect).
   После интерьера каждый сектор — одна связная область; проверить `findRegions` на
   под-сетке, при провале — перегенерировать интерьер (до 5 попыток), потом откат в `open`.
4. **Граф.** Соседство секторов = общая стена длиной ≥ 3 (с учётом углов). Остовное дерево по
   случайным весам + `extraEdges` случайных рёбер из оставшихся соседств. Если граф соседств
   несвязен (BSP это гарантирует связным, но проверить) — бросить, попытка заново.
5. **Шлюзы.** На каждое ребро — ровно один тайл `Airlock` на общей стене, в точке, где по обе
   стороны пол (искать кандидатов; если нет — прорубить 1 клетку пола с каждой стороны).
   Никаких других отверстий в рамках. Записать в `zone.airlocks` обеих зон.
6. **Вход и люк.** `entryHint` — в зоне `entryIn` (если задана) иначе в листе с наименьшим id.
   Люк ставит пайплайн (`farthestWalkable`) — но если `stairsIn` задан, вернуть в
   `BuildResult` подсказку `stairsHint` и научить `assemble()` уважать её (самая дальняя
   клетка **внутри указанной зоны**).
7. Вернуть `tiles`, `rooms` (комнаты интерьеров, для `Level.rooms`), `zones`, `entryHint`.

Всё через `ctx.rng` (использовать `rng.fork` на сектор — детерминизм).

## Пайплайн после строителя

`assemble()` вызывает `enforceBorder`, `connectRegions`, `placeVaults`, `sealUnreachable`,
`placeDoors`. Для `DeckBuilder`:

- `connectRegions` должен быть no-op (одна область). Добавить в `LevelSpec` и в
  `MapgenOptions` (пробросить в `generateLevel`) `connect?: boolean` (default true); карты `DeckBuilder` идут с `connect: false` — иначе
  любая ошибка строителя молча зарастёт туннелем сквозь зону. Пусть падает в тесте.
- `placeVaults` общего пайплайна для палуб не используется (`vaultCount: 0`); зональные
  storylets стампует E6 внутри строителя.
- `placeDoors` работает как есть (с правкой E4 про соседство со шлюзом).

## Тесты (`tests/deck.test.ts`, property, 200 сидов × 8 глубин, как `mapgen-family.test.ts`)

- Валидатор `validate()` без проблем на каждой карте.
- **Изоляция зон:** для каждой пары проходимых клеток-соседей (8-связность) либо одна зона, либо
  хотя бы одна из них — `Airlock`. Это главный инвариант.
- Каждая зона: ≥ 1 шлюз; `rect` не пересекается с другими; `zoneAt` покрывает все проходимые.
- Число шлюзов = число рёбер; граф зон по шлюзам связен.
- Вход в `entryIn`, люк в `stairsIn`, когда заданы.
- Детерминизм: два вызова с одним сидом → идентичные `tiles` и `zones`.
- Все три стиля интерьера встречаются на 200 сидах.
- Время: 200×8 сборок < 20 с на ноутбуке (иначе тесты станут пыткой).

## Откат

Если к вечеру дня 5 инвариант изоляции не держится: оставить BSP-секторы + `open`-интерьер
(это тривиально изолируется), стили `rooms`/`cluttered` выкинуть. Написать в статусе.

## Чего не делать

Не переписывать существующие строители; не трогать `builderForDepth`; не добавлять зонам
ничего, кроме `kind/name/rect/airlocks`.
