## Главное: наш FOV подтверждён двумя независимыми источниками

`prism/engine/algorithms/fov/` — это **тот же symmetric shadowcasting Альберта Форда**,
что и наш `sim/shadowcast.ts`: квадранты с матрицей трансформации, `Row(depth,
startSlope, endSlope)`, `Fraction`, `isSymmetric`, `roundTiesUp/Down`, итеративный скан
вместо рекурсии. Совпадает вплоть до имён функций.

В libtcod он лежит отдельным алгоритмом `FOV_SYMMETRIC_SHADOWCAST`, и в шапке файла
прямо стоит:

```c
/** \file
    Symmetric Shadowcasting algorithm.
    Based on: https://www.albertford.com/shadowcasting/
 */
```

То есть оба профессиональных инструмента жанра пришли к тому же алгоритму. rot.js его
не имеет — отсюда и замеренные нами 9–11 % асимметричных пар.

### Где мы строже обоих

Оба считают наклоны во **float**:

```lua
-- prism, engine/algorithms/fov/row.lua
function Row.roundTiesUp(n)  return math.floor(n:tonumber() + 0.5) end
```
```c
// libtcod, fov_symmetric_shadowcast.c
static float slope(int row_depth, int column) { return (2.0f * column - 1.0f) / (2.0f * row_depth); }
static int round_half_up(float n) { return (int)roundf(n * (1 + FLT_EPSILON)); }
```

libtcod даже вводит поправку на `FLT_EPSILON`, чтобы округление не срывалось.
У нас вся арифметика наклонов целочисленная — сравнение `col * den >= depth * num`
вместо деления. Это то самое пятое свойство из шести у Форда («никаких артефактов
округления»), и оно у нас выполняется по построению, а не приближённо.

Честная оговорка: на практике float с эпсилоном работает, и утверждать, что у них
из-за этого баги, у меня оснований нет. Мы просто не вносим этот класс краевых случаев.

### Заодно: похоже, в prism есть настоящий баг в проверке границ

Во всех трёх проверках `fov.lua` координата `y` сравнивается с **шириной** карты:

```lua
if x < 1 or y < 1 or x > level.map.w or y > level.map.w then return end
```

При этом у `Map` есть отдельное `h` (`map.lua:79`: `y >= 1 and y <= self.h`). На
типичной неквадратной карте 80×40 FOV будет запрашивать клетки ниже нижней границы.
Урок для нас прямой: один `Grid.inBounds()` на весь проект вместо повторяющихся
ручных сравнений — и такой опечатки просто негде появиться.

## Что взято из prism и уже внесено в наш каркас

### 1. Модификаторы статов вместо захардкоженных полей

У prism статус — это `Condition`, набор из `ConditionModifier`, сгруппированных по
прототипу. Смысл: статус не знает, какое производное значение он меняет; он объявляет
модификаторы, а одна функция их разрешает.

Было у нас: `StatusDef.speedMul` и `StatusDef.fovMul`, каждое читается своей функцией.
Добавить «кольцо даёт +2 к защите» — значит писать третью функцию.

Стало (`sim/status.ts`):

```ts
export type Stat = "speed" | "fovRadius" | "defense" | "damageBonus";
export interface Modifier { mul?: number; add?: number }

slow:  { name: "slowed",  modifiers: { speed: { mul: 0.5 } }, opposes: "haste" },
blind: { name: "blinded", modifiers: { fovRadius: { mul: 0.15 } } },

export function modifiedStat(e: Entity, stat: Stat): number
```

`effectiveSpeed`, `effectiveFov`, `effectiveDefense` — тонкие обёртки. Бой теперь
читает `modifiedStat(attacker, "damageBonus")` и `effectiveDefense(defender)`, а не
поля напрямую, и заодно проводит урон через щиты, возвращая `absorbed` отдельно.
Новый модификатор — строчка в таблице, ни одной новой ветки в цикле хода.

### 2. Несколько систем вместо одного твиста

В prism `Level:perform` оборачивает каждое действие вызовами
`systemManager:beforeAction` и `afterAction`, и систем может быть сколько угодно.

У нас был ровно один `Twist`. Стало: `new Game({ seed, twist, systems: [...] })`,
хуки проходят по списку по порядку — главная механика первой. Практический смысл:
голодный счётчик, подкрепления или правило подсчёта очков живут отдельными
объектами, а не дописываются в `game.ts` посреди хода. Рендер собирает
`overlayGlyphs` и `statusLine` со всех систем.

Обе правки покрыты `tests/systems.test.ts` (12 тестов), общий счёт — **196**.

## Что рассмотрено и сознательно не взято

### Target как объект-валидатор с билдером

Самая сильная идея prism. Действие объявляет список `Target`, каждый — цепочка
требований, и валидация происходит в одном месте:

```lua
Target():with(Health):without(Dead):range(6):filter(function(level, owner, t) ... end)
```

Плюсы: одно действие может иметь несколько целей («брось предмет X в существо Y»),
валидация переиспользуется интерфейсом и ИИ, у цели есть `hint` — подсказка UI, как её
выбирать.

Почему не взяли: наш `targeting.ts` уже валидирует дальность, линию взгляда и наличие
цели в одном месте, и этого хватает для набора способностей масштаба джема. Полный
билдер осмысленен там, где действий десятки. Если на дне 6 окажется, что способностей
много и правила у них разные — вернуться сюда, работа на пару часов.

### Decision через корутину

`Level` в prism приостанавливается и «выдаёт» интерфейсу `ActionDecision`, который тот
заполняет. Красивое разделение движка и UI — ровно то, о чём пишет Nystrom.
У нас `playerCommand()` возвращает `Outcome` синхронно: проще, тестируется без
корутин, и на одном игроке разницы нет.

### ECS с отношениями

prism хранит связи вроде `sees` / `seenBy`, `inventory` / `heldBy` как двусторонние
отношения между сущностями, с запросами через `Level:query(...)`. Мощно и оправданно
на 37 000 строк. У нас плоская структура `Entity` — на пятнадцати видах монстров она
и быстрее, и читается без документации.

### Полный ECS (flecs)

Автор The Fiend in Facility 14 взял flecs и с ним занял третье место — но он же пишет
в девлоге, что главный вывод джема для него: «делать больше предварительной проектной
работы». Не архитектура была узким местом.

## Что есть в libtcod, чего нет у нас

Проверено по заголовкам `src/libtcod/*.h`. Из отсутствующего у нас практическую
ценность для джема имеет немногое:

| Модуль libtcod | Есть у нас | Комментарий |
|---|---|---|
| FOV (6 алгоритмов, вкл. symmetric) | ✅ symmetric | шесть вариантов нам не нужны |
| BSP, bresenham, A*/Dijkstra | ✅ | наш Dijkstra мощнее, см. ниже |
| `noise.h` (Перлин, симплекс) | ❌ | пригодился бы для рельефа/биомов, не для подземелья |
| `heightmap.h` | ❌ | то же |
| `namegen.h` (слоговые имена) | ❌ | **дёшево и добавляет флейвора**: процедурные имена уровней и врагов |
| `console_rexpaint.h` | ❌ | чтение `.xp` из редактора REXPaint — так делают вольты «по-взрослому»; у нас вольт это ASCII-строка в коде, для джема достаточно |
| `parser.h` / `lex.h` | ❌ | контент из внешних файлов; у нас контент это TS-таблицы, что типобезопаснее |

### Наш Dijkstra мощнее, чем у prism

`prism/engine/algorithms/dijkstra.lua` — наивный BFS: очередь в виде таблицы с
`table.remove(frontier, 1)` (снятие с головы за O(n)), единичная стоимость шага, без
весов и без карт безопасности.

Наш `sim/dijkstra.ts` — релаксация на бинарной куче, поддерживает `extraCost`,
отрицательные стартовые значения (значит и flee-карты по Brogue), комбинирование карт
с коэффициентами желаний. Это не хвастовство, а следствие того, что мы читали статью
Брайана Уокера, а prism в этом месте ограничился базовым случаем.

## Итог

1. **FOV.** Наш выбор совпал с обоими профессиональными движками, а по точности
   арифметики мы их обгоняем. Вопрос закрыт.
2. **Dijkstra.** Мы впереди prism по возможностям — тут заимствовать нечего.
3. **Взято два приёма** — модификаторы статов и список систем; оба уже в коде и под
   тестами.
4. **Отложено осознанно** — Target-билдер (вернуться, если способностей станет много).
5. **Мелочь на потом** — генератор имён из libtcod: дёшево, добавляет характера.
6. **Урок из чужого бага** — единая проверка границ вместо ручных сравнений `w`/`h`.

Стек менять не на что: prism требует Lua и LÖVE, libtcod — C и сборку через emscripten.
И то и другое дороже, чем то, что у нас уже работает и собирается в 82 КБ.
